# Bitácora personal de decisiones

1. El stack que elegí: al tratarse de una solución multiplataforma, decidí ir con el desarrollo del frontend usando react con un css propio. Con react la velocidad del renderizado en el lado web es mas rápido para el cliente, por lo que generaría menos fricción. Para el Backend decidí usar supabase, por ser la alternativa que mas he utilizado para prototipado ultimamente, y por lo tanto se me hizo mas fluido el desarrollo, desde la creacion de tablas, hasta las edge functions creadas para el calculo en el backend.
2. Con la plantilla o estilo inicial finalizado, decidí dar como referencia, el aspecto y estilo del branding usado por Kru.
3. Escogí Claude Opus 5.5 para el trabajo mas intensivo, es decir, de crear arquitectura, dar el estilo basado en la referencia que le dí y a Sonnet 5.5 para despleigues y conexiones con la base de datos.
4. Ya una vez con la version 1 del MVP, empecé a hacer las pruebas en local, y en paralelo a crear data mock up para pruebas o simulaciones.
5. El despliegue a un dominio lo hice mediante la herramienta pages de Cloudflare, con un subdominio propio.
6. Luego de dicho despliegue, empecé con las pruebas en el móvil, utilizando ambos roles, y buscando fallas, bugs o inconsistencias.
7. Durante las pruebas en móvil, tuve problemas de red en mi casa, por lo que me dio la idea de dar prioridad al offline-first en la aplicación y asi mejorar el UX durante fallas de conectividad que son recurrentes en algunos sitios de trabajo.
8. El último punto me llevó a la siguiente consideración: la persistencia de datos, o que pasa si un colaborador marca sin red en su telefono, entonces en este caso tome la decision de dar la opcin de descargar el app desde el navegador, lo cual permite acceder exactamente igual como una app nativa desde el movil, bien sea android o iOS y ademas nos permite mantener los estados de los parámetros o en este caso, el marcaje de acuerdo a la ultima carga que se hizo cuando si tenia red el usuario.
9. La arquitectura inicialmente elegida fue MVC (model view controller), pero para el offline first me di cuenta de que no seria la ideal ya que el modo offline necesita logica en el cliente, con vistas renderizadas en el servidor y sin red no se puede ni abrir la pantalla de marcar.
10. Tomé la decisión de ir por una arquitectura de 3 capas, es decir, una progressive web app (PWA) instalable como frontend, una API con la lógica en edge functions de supabase y una base postgresql para datos. De esta manera el renderizado del front se hace en el navegador y no en el servidor y elimina la dependencia de red para el marcaje.
11. Luego llegué al punto de considerar los metodos de proteccion de las APIs y datos de la base, pense que usar las RLS policies para cada tabla, pero esto implicaba que el frontend se comunicara directamente con cada tabla con los permisos correspondientes, y un atacante podría controla el cliente, puede saltarse la interfaz y enviar cualquier consulta.
12. Para mitigar lo anterior decidí que cada operacion debe pasar por la API, supabase auth debe reconocer al usuario, otorgar un JWT o token, y solo con este token valido poder alterar los datos de las tablas dependiendo del rol del usuario en cuestion.
13. Decidí agregar refrescamiento automatico del app para evitar que el usuario tenga que refrescar manualmente.
14. Añadí una bitacora de decisiones por parte de RRHH para llevar registro de solicitudes de colaboradores, como cambios de turno y permisos.
15. Para evitar marcajes accidentales, cambie boton para marcar por un Slider.
